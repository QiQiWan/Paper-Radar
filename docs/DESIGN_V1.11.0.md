# Paper-Radar 文献追踪系统设计方案与分阶段实施路线

**版本基线：v1.10.0；本次实现：v1.11.0；日期：2026-11-04**  
**适用对象：** 日常跟踪一个或多个科研方向、维护 Zotero 文献库并定期生成组会或个人研究报告的用户。  
**实现原则：** 保留本地 Python + SQLite + 无前端框架的 Web 工作台；先解决跨主题数据串扰和阅读推荐，再逐步扩展全文分析。所有云端模型功能须明确告知数据范围和费用，并可关闭。  
**声明：** 本文将“已实现 / 已自动测试 / 需要实机核验 / 后续计划”分别标明。方案中的数值目标是拟议验收标准，不能当作已达到的效果。

## 1. 结论与产品边界

v1.10.0 已能完成多来源检索、文献合并、Zotero 收藏夹分析、中文摘要和自动更新提醒。下一阶段最有必要提高两方面能力：一是确保不同研究课题拥有独立的文献评价、阅读状态和推送结果；二是帮助科研人员从大量检索结果中找到真正需要阅读的论文，并说明推荐依据。

建议逐步建立以下工作闭环：

1. 用户创建研究主题，定义研究目标、边界与英文关键词。
2. 检索器依次查询公开来源和授权来源，按日期、许可与元数据质量过滤。
3. DOI 等稳定标识合并同一论文；数据库只保留一份原始题录和 PDF。
4. 各主题独立计算推荐分数，用户可以反馈“相关 / 不相关”，不干扰其他主题。
5. 需要时启用 OpenAlex 语义发现和云端大模型推荐重排序；模型给出的推荐理由须附标题或摘要中的原文片段。
6. 各主题按独立目录生成 Word、Markdown 和 CSV；Windows 计划任务可以按顺序更新全部主题。
7. 任务执行历史保留时间、检索来源、数量和错误，便于复核数据是否缺失。
8. 更高版本再加入全文 PDF 证据解析、论文方法对比、基于证据的文献问答。

### 1.1 三种使用层级

| 层级 | 需要用户提供的条件 | 具备的能力 | 默认设置 |
| --- | --- | --- | --- |
| 基础检索 | Python 与网络连接；某些来源需要 API 凭据 | 公开元数据检索、去重、主题管理、PDF、报告 | 默认开启 |
| 智能推荐 | 自选云端模型 Key；语义来源依其官方额度使用 | AI 检索词规划、标题摘要重排序、推荐理由 | 默认关闭，按需开启 |
| 深度研究（规划） | 合法获取的全文、计算资源和模型配额 | 结构化全文提取、跨论文比较、证据问答 | 尚未实现 |

## 3. 核心数据模型

### 3.1 数据组织

`papers` 继续保存跨主题共享的题名、摘要、作者、DOI、发表日期、原始 URL、开放获取信息、PDF 下载状态和摘要缓存。主题关联表 `topic_papers` 则保存 `topic_id`、`paper_id`、`score`、`is_starred`、`reading_status`、`feedback`、`ai_relevance`、`recommend_reason`、`recommend_evidence`、`rerank_fingerprint` 和 `matched_at`。

这样同一 DOI 在多主题中只对应一份题录和 PDF，而两个主题可以将同一论文分别标记为“已读”与“未读”。从本版本开始，论文库默认只展示当前主题已收录的论文，并提供“所有已收录文献”视图，便于重新挑选跨主题成果。

老版本数据库没有逐主题来源记录。升级时采用保守策略：将旧版共享记录保留在默认研究主题；此前创建的其他主题需要重新执行一次检索，才能重建准确的主题关联。数据库迁移保留原始 `papers` 字段，不主动删除个人记录。由于历史追踪关系没有被记录，本程序无法可靠反推出所有旧文献属于哪个非默认主题。

### 3.2 数据与任务文件

| 文件 | 用途 | 数据敏感性 |
| --- | --- | --- |
| `settings.json` | 主题列表、各主题关键词和检索参数、模型选择、更新检查设置 | 研究兴趣信息，备份时避免公开 |
| `data/papers.sqlite3` | 统一论文库与 `topic_papers` | 可能包含用户阅读偏好，不应上传公共仓库 |
| `data/run_history.sqlite3` | 有界任务历史记录（最多 1500 条） | 保存状态/数量/耗时等摘要，不保存原始论文全文与 API 密钥 |
| `data/update_check.json` | GitHub Release 检查缓存 | 无论文全文与密钥 |
| `reports/` | 默认研究主题报告 | 可能包含研究兴趣和用户批注 |
| `reports/themes/<id>/` | 非默认主题的报告 | 同上 |
| `downloads/` | 合法获取的 PDF | 按论文原有许可使用，勿直接公开再分发 |

## 4. 文献发现策略

### 4.1 来源角色

默认来源继续是 arXiv、OpenAlex 和 Crossref；Springer、Scopus、ScienceDirect 根据用户的 API 凭据和订阅权限决定是否开启。v1.11 追加可选的 `OpenAlex 语义发现`。它用于寻找表述不同、语义相近的论文，不能保证覆盖全部文献。根据 OpenAlex 官方接口说明，语义查询采用 `search.semantic`，单次最多获取 50 条结果，存在独立额度和速率约束；应查看最新官方费用和限制。

### 4.2 多关键词与配额

v1.10 已采用多查询：arXiv 使用一条组合检索，其余适用来源将前若干关键词分别查询，再轮询合并结果。v1.11 保留并增强诊断，允许人工设定每来源 1–20 个查询词、选择需要启用的来源，并记录部分失败。未来可把词组进一步整理为“核心检索 / 扩展检索 / 排除条件”，根据每组命中质量动态分配预算。

开放数据的日期口径、检索频率和来源类型并不完全相同。本地结果仅可解释为“系统在给定来源与检索条件下实际发现的记录”，不得直接写成领域全部论文。

### 4.3 检索质量优化路线

第一阶段：按研究主题分别维护用户关键词，保留生成的查询词供用户修改。第二阶段：保存每条子查询的结果数量、重复率、最终入选率，以真实效果判断是否扩展。第三阶段：在获取数据后进行关键词、向量和重排序的混合召回；需要人工建立测试集后确定权重。

## 5. AI 推荐排序：任务规则与证据边界

### 5.1 模型处理范围

为控制成本，默认关闭 AI 推荐。用户开启后，每次最多对本主题的 30 篇候选论文进行分析，默认上限为 15 篇，每批最多 8 篇。传输内容为研究目标、标题和摘要的截断版本，不上传本地 PDF、Zotero 私有笔记与工作目录。模型无法访问文件系统，也没有下载、写库或执行其他操作的工具权限。

模型返回与论文 ID 对应的 0–3 级相关性，以及中文推荐理由、来自题名或摘要的连续原文片段。程序逐条验证 JSON 类型、论文 ID、等级范围、文本长度和证据能否在来源文本中找到。无效结果保留确定性关键词排序；调用失败、密钥缺失或模型响应异常都不会阻止生成常规报告。

已验证的模型结果按论文题名、摘要、研究目标、检索关键词、模型和提示词版本计算指纹，重复调用前先查找当前主题的缓存。研究目标或模型变化后，重新运行检索可触发再次分析。API 收费遵循用户实际选择的服务商规则。

### 5.2 相关性与用户反馈

确定性相关度继续基于特定研究词匹配：标题命中赋予较高权重，摘要命中赋予次级权重，泛化词无法单独使论文入选。可选语义来源在缺少词面匹配时给予低等级探索候选标记。有效模型证据提供有限的附加排序信号，人工正反馈额外提高优先级；人工负反馈会从当前主题的近期阅读列表中排除，并保留其原始题录。

注意：模型给出的“值得阅读”属于针对给定研究目标的建议，不等同于论文经过同行评审、实验结果有效或其创新性已得到证实。摘要级报告不应凭空写出实验指标、研究空白或软件复现结论。

### 5.3 后续混合推荐引擎设计

计划增加可选 Embedding 路由，使用关键词、向量相似度、历史阅读反馈和论文新鲜度进行多目标排序。初期只提供线性加权基线；在人为标注的相关性样本集上优化权重，避免直接采用难以解释的黑箱分数。离线评估需要同时报告高相关论文召回、排序质量、误推率和处理成本。

## 6. 自动追踪、任务状态与恢复

v1.11 新增两种运行方式：“只追踪当前研究主题”和“依次追踪全部研究主题”。批量任务在启动时冻结所有主题配置，逐个执行，不会在后台更改网页当前选中的主题。每个主题分别生成报告，完成后记录检索数量、新增数量、报告入选量以及成功/失败状态；单一主题失败时继续执行后续主题。如果全部失败，任务状态为失败；部分成功，任务状态为部分完成。

Windows 用户可将“每日追踪全部主题”保存到原有计划任务配置，指定时间仍由系统任务计划程序控制。电脑离线、休眠、关闭或账户权限不足会影响执行。其他系统的图形化后台任务安装仍是后续工作。

已保存的运行历史可以帮助确认是哪次执行失败及哪些来源返回了数据。但当前还没有按论文逐条持久化的下载/解析任务 DAG，也没有完整的中途继续执行机制；这部分属于后续迭代。

## 7. 前端页面与最简交互

主工作台继续优先展示“研究主题 → 关键词 → 一键检索 → 近期文献”；高级 AI 规划、来源配置和每日后台任务保持折叠。多主题切换后，当前主题的论文库、报告和推荐状态应立即刷新。

- 工作台：研究主题选择器、新建/重命名/删除、AI 研究目标、主检索按钮和批量主题按钮。
- 论文库：默认显示当前主题；可切换全库、搜索、按阅读状态筛选；每篇提供星标、已读状态、相关/不相关反馈和来源链接。
- 设置：可选 AI 推荐、单批候选篇数、来源/额度提示、自动更新与运行历史。
- 报告：优先突出研究问题、为何值得读、摘要级证据与待核查内容，避免无依据的“突破性”“显著提升”等判断。

移动端布局优先保证按钮和输入框可点、无横向滚动。未来考虑将页面导航进一步缩减至“今日发现、研究主题、论文库、设置”，需要避免破坏现有 Zotero 与报告页面入口。

## 8. 全文理解与 RAG：下一阶段技术设计

### 8.1 全文处理流水线（未实现）

1. 仅接收有明确授权或可合法访问的 PDF；原样保留来源 URL、许可证和版本。
2. 使用 Docling、GROBID 等可选解析器提取章节、表格、参考文献、公式等；对应解析器需要单独安装和环境检测。
3. 为正文片段保存 `paper_id + version + page + section + text + parsing_confidence`；在表格或公式解析失败时人工核查。
4. 根据固定 JSON 结构提取研究问题、模型架构、数据集、基线模型、实验指标、结果与局限，保留每条结论的来源定位。
5. 后续专题比较时仅并列评价数据集、指标和实验条件可比的结果；无法对齐时显示“比较条件不同”。
6. 文献问答先检索本地原文片段，再生成回答；没有证据时拒绝提供确定性结论。

### 8.2 建议新增的数据表（规划中）

`paper_versions`：预印本与发表版本映射。`paper_chunks`：全文段落和页码。`paper_claims`：方法、实验结果和原文证据。`retrieval_index`：可选向量索引。`analysis_jobs`：分阶段任务恢复状态。

不建议一开始引入重量级独立向量数据库。可以先使用 SQLite 全文搜索与轻量向量索引做小规模验证，确认实际检索质量后再评估 PostgreSQL/pgvector 等替代方案。

## 9. 发布、安全及合规

- 本地服务只监听 `127.0.0.1`，写请求保留本地 Token 和来源限制；不要直接向公网暴露。
- 模型输出与论文正文都属于不可信数据，不能获得本地 Shell、下载任意网址、覆盖 Zotero 文件或写入配置的权限。
- `settings.json` 不保存模型 API Key；源码 ZIP 排除数据、缓存、PDF、日志和本机密钥文件。
- 仅使用官方公开 Release 元数据检查更新；发现新版只弹提示并跳转官方发布页面，不自动替换本机文件。
- 开启第三方云端 AI 前，应明确告知用户发送的字段、潜在费用、服务商的保留政策；涉及未公开研究数据时默认关闭。
- 出版社 API Key 与订阅授权不足的场景应显示诊断，不绕过付费墙、不承诺全文下载成功。
- 每次版本发布必须更新 `paper_radar/__init__.py`、`pyproject.toml`、前端版本号、`CHANGELOG.md`、README 和升级说明。

## 10. 实施优先级与验收标准

| 阶段 | 主要交付 | 计划验收方式 |
| --- | --- | --- |
| v1.11.0：已完成 | 主题级匹配记录、相关性反馈、AI 证据重排序、可选 OpenAlex 语义发现、多主题批量运行、运行历史、版本同步 | 新旧数据库兼容测试；跨主题一致性测试；模拟模型和 API 失败；Python/JS 检查；桌面/移动端静态页面 QA |
| v1.11.x：推荐质量评估 | 人工标注文献集、Precision@10、Recall@50、NDCG@10、成本/运行时统计 | 至少 2–3 个方向、约 300 篇人工标注；与 v1.10 原算法做盲测比较 |
| v1.12：PDF 全文解析 | 合法 PDF 抽取、分页/节定位、表格与公式失败标记、可追溯方法实验卡片 | 人工核对不同来源的 PDF，量化正确抽取比例和证据引用准确率 |
| v1.13：研究报告升级 | 多论文技术路线比较、专题周报/综述、用户反馈编辑 | 每个技术结论有引用定位；报告中不包含未经核实的数值与“研究空白”断言 |
| v2.0：文献知识助手 | RAG 问答、引用版本跟踪、Zotero 授权回写、可恢复任务队列 | 文献问答真实准确率、完整度、边界声明、回写冲突和恢复测试 |

拟议的质量门槛：Precision@10 ≥ 0.80、Recall@50 ≥ 0.90、NDCG@10 相对旧版提升 ≥ 15%，以及结构化数值的证据可定位率 ≥ 95%。这些均须以人工标注与可复现实验测得。模型供应商成本与运行时间同样应作为每次评估的输出。

## 11. 升级及回滚

1. 退出 Paper-Radar 与相关后台 Python 进程；如计划任务可能运行，应先关闭或暂停。
2. 备份整个旧目录，至少保存 `settings.json`、`data/`、`reports/`、`downloads/`、`logs/`。
3. 用新版**程序文件**替换旧代码；保留全部个人数据，不应拿空白发行包的 `data/` 覆盖原库。
4. 打开工作台，先验证主题和旧报告存在，再执行一次仅更新本地报告；必要时对其他主题重新检索以重建主题归属。
5. 验证新主题独立标记和多主题运行记录；按需开启云端 AI/语义发现。
6. 如需回滚，应恢复备份的完整数据库和对应版本源码，避免旧程序写入包含新字段的数据库后发生不兼容。

**当前验证边界：** 回归测试和离线页面模拟可以保证大量逻辑分支正确，无法替代真实出版社账号、OpenAlex 费用账户、云端模型输出、Zotero 真实数据库和 Windows 定时任务的端到端实测。
