## 一、问题判断

用户截图中，**本地页面仍能加载**，左侧导航和任务状态也正常显示；点击 **生成检索词** 后，按钮附近显示“生成失败”，右上角出现“服务处理失败”。因此首先怀疑关键词生成接口和异常处理链路，不能仅据截图认定所有后端接口均不可用。

在干净的隔离用户目录中启动 v1.49.0，首页、文献库、主题及状态接口均可返回 HTTP 200。将模型配置为已授权且具有测试密钥、但服务地址指向不可用的 `127.0.0.1:9`，调用 `POST /api/ai/plan` 可以复现：接口返回 HTTP 500，前端映射为通用“服务处理失败”，系统未留下与这次 HTTP 错误关联的异常堆栈。此处是可确认并已修复的故障链条。

原设备的真实异常日志尚未取得，所以不能排除另有磁盘占满、数据库锁定、配置损坏、网络代理或其他错误。本次同步为这些故障增加可定位的日志和错误编号，后续再次失败时可快速收敛原因。

## 二、根因与改动对应关系

| 问题 | v1.49.0 表现 | v1.49.1 改动 |
|---|---|---|
| 模型服务不可达 | 泛化为 HTTP 500 | `MODEL_CONNECT_FAILED`，返回 HTTP 424 与中文建议 |
| 密钥/额度/权限/接口配置异常 | 混入一般 RuntimeError 或 500 | 区分 `MODEL_KEY_MISSING`、`MODEL_AUTH`、`MODEL_BILLING`、`MODEL_RATE_LIMIT`、`MODEL_CONFIG` 等 |
| 本地凭据管理器异常 | 无法直观判断 | 单独的 `CREDENTIAL_ACCESS` 错误类型 |
| 服务内部意外异常 | 报错但无可追溯编号 | 生成 12 位请求编号，记录错误类别和 Python 调用位置 |
| 数据库/存储异常 | HTTP 503 缺少关联诊断编号 | 写入 `storage_error` 记录并返回编号 |
| 用户需要随时提交日志 | 分散在检索、任务或启动文件中 | 页面多入口一键下载结构化 ZIP；脱离网页也可导出 |
| 初次启动可能错误识别已有工作空间 | 过早写入日志干扰空工作空间判断 | 先初始化默认配置，后创建运行日志 |
| 任务准备或启动失败 | 任务状态可能停留在运行中 | 恢复 busy 状态并记录 `task_preparation_failed` / `task_start_error` |
| 旧版后台服务仍在运行 | 新版启动器可能静默打开旧页面 | 比对同一用户的服务版本，提示安全停止旧服务 |
| 已进入只读配置恢复模式 | 常规 POST 操作被封锁 | 保持用户业务写入封锁，但允许安全下载已有日志 |

## 三、日志的具体设计

新模块 `paper_radar/runtime_diagnostics.py` 管理 `logs/runtime.jsonl`。日志为按行 JSON，默认包含 UTC 时间、事件类别、接口路径（删除查询字符串）、状态码、耗时、错误代码、错误编号、异常类名以及源文件/行号/函数名。单文件写入约 2 MB 后轮转，保留当前文件及两份历史文件。

本地工作台通过 `POST /api/diagnostics/export` 导出日志 ZIP；此操作使用页面的本地安全令牌。默认 ZIP 包括结构化日志、清单和阅读说明。系统不会主动将 API Key、密码、Cookie、模型请求正文、研究问题或 PDF 全文写入结构化日志，也不会自动上传数据。

用户可以主动勾选 **附加任务日志**，额外包含 `manual.log`、`scheduled.log` 和 `web_server.log` 的限长内容。这些日志可能包含研究主题和业务输出，程序执行常见凭据字符串的尽力清理，但用户向外分享前仍应检查附件。结构化日志写入失败不会让业务进程直接崩溃。

前端入口：顶部导航“下载运行日志”；错误提示卡片“下载运行日志”；右下角任务详情“下载运行日志”；设置 → 运行记录 → “系统错误与请求”及下载操作。

非网页入口：Windows `start_windows.bat --diagnostics`，macOS/Linux `./start_macos_linux.sh --diagnostics`；`--include-task-logs` 可明确选择附加任务日志。导出位置为用户 Downloads 目录（无该目录时回退当前工作目录）。

## 六、仍需现场验证

1. 故障电脑的原始原因。请在原设备上部署修复版，重新尝试“生成检索词”；若仍失败，请下载默认日志 ZIP 和错误编号。原因需要以该设备的日志为准。
2. 真实服务商 API 的密钥权限、余额、网络/代理和模型响应；本次未使用收费模型 API 进行联网验收。
3. Windows/macOS/Linux 原生桌面安装、自动更新以及用户数据目录权限；本次在隔离 Linux 环境运行，未在原设备操作。
4. 磁盘损坏、OneDrive 同步、数据库被其他进程锁定、无空间等高风险环境仍需使用真实备份和故障场景验证。
5. 公网多用户门户具有独立运行与审计机制；本次新增的页面级日志 ZIP 属于**本地工作台**。公网管理日志导出需要独立的权限设计和验收。

## 七、升级与排查建议

保留原用户数据目录，先备份，再从旧版 **设置 → 运行记录 → 停止本地服务** 安全停止后台进程。如果任务仍在执行，先等任务完成。将 v1.49.1 解压到新的程序目录，运行原平台的统一启动脚本。新程序会检查后台版本，不再静默复用旧版服务。

升级后，先尝试普通关键词检索（不依赖模型），再按需要配置模型并尝试生成检索词。若普通操作也失败，下载默认运行诊断 ZIP；若网页无法打开，使用命令行 `--diagnostics`。分享日志前请保留默认不附加研究任务日志的设置，除非维护人员明确提出需要。

更详细的操作步骤见 `docs/RUNTIME_DIAGNOSTICS_V1491.md`。
