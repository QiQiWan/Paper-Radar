# Paper-Radar v1.10.0：功能、可靠性和版本更新审查

版本：1.10.0 ｜ 迭代日期：2026-11-04 ｜ 依据：用户提供的 v1.9.1 完整源码与文档

## 一、结论

v1.9.1 已具备多学术来源、Zotero 收藏夹、云端模型摘要和 AI 检索词规划。本轮重点解决长期研究配置互相覆盖、各检索源只使用前几组关键词，以及用户无法获知新发布版本的三个实际问题。保留现有 Python + SQLite + 本地 Web 工作台的结构，不改变论文库与原始 PDF 存储方式。

## 二、已实施的功能

| 编号 | 功能与代码位置 | 具体行为 | 风险与边界 |
| --- | --- | --- | --- |
| U-01 | `updates.py` | 后台查询 GitHub 正式 Release、比较语义化版本号、每日检查并持久化上次结果 | 不自动下载安装；依赖公共互联网和仓库 Release |
| U-02 | `webapp.py` `/api/update*` | 工作台启动后启动后台检查；提供手动检查、当前状态和忽略指定版本操作 | 断网时返回清晰状态；不阻塞 HTTP 页面 |
| U-03 | `static/index.html`、`app.js`、`app.css` | 有新版本时出现顶部提示，设置中可配置检查频率和开关 | 不把没有 Release 的仓库描述为“最新版本” |
| T-01 | `topics.py`、`core.py` | 创建、切换、重命名、删除主题；每个主题单独保存检索词、来源、Zotero 关联和相关检索参数 | 数据库、PDF、模型密钥仍共享；默认主题报告路径不变 |
| T-02 | `get_output_dir` | 默认主题继续输出 `reports/`；新增主题输出 `reports/themes/<ID>/` | 删除主题只删除配置引用，历史报告不会自动删去 |
| S-01 | `sources/base.py` | 除 arXiv 使用组合查询外，其他来源按关键词发起多组独立查询；对各组结果去重、轮流取样、再做本地相关性排序 | 查询上限默认每源8组，可调1—20；增加 API 使用量和耗时 |
| S-02 | Word/Markdown | 每来源保存成功数、耗时、部分失败标记；后续可结合查询记录排查漏检 | 来源成功不保证全部查询成功，报告予以区分 |
| DOC-01 | `CHANGELOG.md`、`docs/` | 增加版本更新记录、升级指南、发布检查清单和用户操作说明 | 正式发布需 GitHub 上创建公开正式 Release |

## 四、仍有待推进的工作

**P1：语义召回与个性化排序。** 当前仍以关键词与 Zotero 文本匹配为基础，多查询改善了查询词利用率，但不能保证召回语义上相近、文字不同的论文。建议增加可选 Embedding + 关键词混合排序，并建立人工标注的 Precision@10、Recall@50 测试集。避免在没有实测数据时宣称推荐精度提升。

**P1：端到端版本提示实机验收。** 自动化测试模拟 GitHub 响应，尚需在真实 Windows 网络和已公开 Release 上验证连接、限流与提示显示。若远程尚无正式 Release，应该显示“暂无可访问的公开 Release”，不会产生新增版本提示。

**P2：跨主题独立的后台计划。** 当前 Windows 每日任务继续按**任务触发时的活动主题**执行。尚未实现同时为多个主题分别设置定时计划。报告按主题隔离，论文库和下载目录是共享的。

**P2：全文结构化理解与证据问答。** 当前模型速览主要使用标题和摘要，尚未实现完整 PDF 解析、章节/页码证据定位、跨论文方法对比和知识库问答。

**P2：出版社 API 限速与全面测试。** 多查询能覆盖更多术语，但不同来源的授权、配额和响应速度有差异。应进一步提供每来源查询上限、错误分类和账户配额上限；正式使用请根据实际 API 限制调整频率。

## 五、推荐验收流程

1. 从 v1.9.1 的 `settings.json` 和 `data/papers.sqlite3` 直接启动 v1.10.0，确认原配置与历史论文不变。
2. 新建“复杂几何神经算子”，编辑关键词并保存；切回默认主题后再切回，检查检索参数和报告路径均独立。
3. 使用模拟 API 对第4至第8组关键词分别返回独立论文，检查多查询均执行，并在某组失败时保留其他组的结果。
4. 模拟远程正式版高于/低于本机版本、404、403、超时和恶意 URL，确认更新提醒行为正确。
5. 开启/关闭自动检查、设置检查频率、手动检查、忽略版本；检查页面刷新后仍正确，且检索操作不受更新检查影响。
6. 最后使用有网络的真实 Windows 环境核对 GitHub Release、出版社 API 授权、Zotero 与 Windows 定时任务。


## 六、额外验收：离线 Chromium 与真实本地 API 桥接

使用 Chromium 的 HTML/CSS/JavaScript 页面渲染，将前端请求经测试桥接到真实运行的本地 HTTP 服务，检查了主题创建、切换、配置保存、重命名、删除；更新提示通过模拟高版本 Release 检查显示、官方链接与隐藏逻辑；390px 手机页面文档宽度为390px，无横向溢出及 JavaScript 异常。

本测试采用真实 Python HTTP 接口及真实前端 JS，但由于运行环境的浏览器直接访问 127.0.0.1 受限，网络传输经过测试桥接。该结果不能代替 Windows 本机 Chromium 直接访问服务、真实 GitHub 网络检查和实际发布后更新提示验收。更新条图像属于**模拟较新版本**，不得作为真实 GitHub 新版本发布证据。

## 七、最后修复的升级缓存边界

保留 v1.9.1 的 `data/update_check.json` 更新到 v1.10.0 后，旧缓存可能仍把远程 v1.10.0 标记为 `available`。现在 `UpdateChecker.status` 每次根据当前程序版本与已校验的远程版本重新比较，因此升级后不会出现误报；并再次检查本地缓存的下载页 URL 是否属于项目官方 HTTPS Release 路径。上述两项均新增了回归测试。
