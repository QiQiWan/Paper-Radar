# Paper-Radar v1.15.0：启动自动更新系统设计与验收

版本日期：2026-11-04。目标：在不破坏既有文献追踪、模型 Agent 和个人科研数据的前提下，实现启动前自动检查并安装 GitHub 正式版本，保证断网可用、安装可审计、异常可恢复。

## 1. 对 v1.14.0 的判断

v1.14.0 的 `paper_radar/updates.py` 已实现 GitHub Release 的后台元数据检查、频率限制及用户通知，但代码明确禁止自动安装。Windows `start_windows.bat` 和 Unix `start_macos_linux.sh` 在创建虚拟环境后直接安装依赖并启动应用；这条链路没有下载、校验、事务管理和回滚能力。现有模型 Agent 可保持不变。本轮已在启动脚本中引入独立的标准库监督层，避免尚未安装 pypdf、docx 等依赖时无法更新。

## 2. 安装与运行的状态机

| 状态 | 触发条件 | 行为 |
| --- | --- | --- |
| disabled | 用户关闭版本检查/自动安装，或使用 `--no-update` | 跳过公网请求，直接检查依赖并启动本地版 |
| running | 已有本地 Web 服务或检测到正在检索的锁 | 禁止热更新，打开现有工作台或继续启动本地版 |
| unpublished | GitHub 没有公开正式 Release / 返回 404 | 使用本地版本 |
| up_to_date | 最新正式版不高于本地版本 | 使用本地版本 |
| error | 网络超时、限流、附件缺失、SHA 不匹配、路径不安全、磁盘不足 | 保持旧版及数据不变，继续启动 |
| updated | 已按事务替换程序文件，等待监督器验证新版启动 | 核查依赖、启动 HTTP 服务器；完成后标记 success |
| success | 新版已通过启动健康检查 | 保留受限数量的旧版备份，可供人工诊断 |
| rolled_back | 新版本未能启动，或上次事务中断后恢复 | 恢复旧版程序；启动失败时恢复原数据库快照 |
| skipped_failed | 同一新版本最近一次失败 | 跳过重复尝试，使用旧版 |
| recovery_failed | 事务/备份损坏、无法完成旧版恢复 | 阻止继续启动，提示维护者处理 |

## 3. 真实性、完整性与威胁边界

本轮只从固定 `QiQiWan/Paper-Radar` 仓库查询公开的、非草稿及非预发布的最新正式 Release。允许更新的唯一 Release 资产名是 `Paper-Radar_v<版本号>_Source.zip`。客户端不安装 GitHub 自动生成的 Source code (zip)，也不接受不含 `sha256:` 摘要或大小信息的资产。

下载使用 HTTPS，限制 URL 初始域名和下载后的重定向域名、传输大小与超时。对 ZIP 提前验证根目录、禁止相对路径穿越/符号链接及未知根文件、限制压缩体积和文件数量；提取后校验 `__version__`、`pyproject.toml`、`__startup_protocol__ = 1`，并解析所有 Python 文件以排除语法错误。SHA-256 与 GitHub API 附件摘要严格一致。该措施保障来源与传输一致性，但不能抵御被攻破的 GitHub 发布者账号；计划商业化时应另外评估独立签名、发布审批与受信密钥轮换。

## 4. 事务与数据隔离

源码管理白名单见 `paper_radar/startup_update.py` 中的 `MANAGED_ITEMS`。个人配置、API Key、Zotero 数据、下载的 PDF、报告、日志、`.venv`、`.git` 和运行中的 BAT/Shell 文件绝不作为自动替换目标。临时安装目录、程序旧版快照、上次检查状态和恢复日志保存在 `.paper_radar_updates/`，与源码位于相同文件系统，即使用户将 `data/` 迁移到独立数据盘，程序文件切换仍可使用 `os.replace`。

在安装前使用 SQLite 备份 API 对 `data/*.sqlite3` 建立事务一致性快照，并保存 `settings.json`。数据库总量大于 512 MB、备份错误或磁盘空余不足时，取消自动安装。旧代码与数据库快照最多保留两轮；用户必须另行安排长期完整备份。升级后若依赖安装或服务器启动失败，恢复此前代码与升级前数据库；若用户在新版本成功工作后主动回退程序，默认保留最新个人数据，避免静默损失研究成果。

安装目录中出现异常符号链接、正在运行的 Web 进程或正在执行的检索任务时，避免替换程序。事务日志在移动程序文件之前写入磁盘；更新途中断电时，下次启动可重放恢复过程。如果恢复阶段本身失败，停止启动，防止混杂新旧源码继续运行。

## 5. 与已有 Agent 和前端的关系

版本更新采用独立标准库启动器，不通过 Language Model Agent 执行下载安装。已有 13 个检索与科研分析 Agent 不获得更高文件系统权限。`GET /api/update` 返回启动更新状态摘要；用户可在“设置 → 软件更新检查”调整是否启动前自动安装，后台版号检查仍然负责运行期间通知。更新下载、依赖安装和本地 HTTP 健康检查的详细故障原因写入启动器状态文件，必要时可用 `--no-update` 进入旧版本排障。

## 6. 发布与迁移

发行人运行 `python tools/package_release.py --out dist/Paper-Radar_v1.15.0_Source.zip` 生成包含固定启动协议的 ZIP 以及本地 `.sha256` 文件。必须在 GitHub 创建正式公开 Release，附件与 Tag 对齐，校验 API `assets[].digest`。因为 v1.14.0 及更早版还没有安装型启动器，用户首次升级 v1.15.0 必须手工替换源码、`start_windows.bat` 和 `start_macos_linux.sh`；之后兼容版才能使用自动安装。

## 7. 本次真实验收和剩余风险

自动化测试覆盖离线启动、无最新版本、正式发布元数据、资产来源和摘要、归档路径防护、版本兼容、实际文件替换、个人数据保护、旧版恢复、数据库快照和启动验证中断。测试依赖本地模拟的 GitHub API，不产生外网模型费用。真实发布端到端下载安装、Windows BAT 与杀软锁文件行为、Linux/macOS 权限、代理/限流与已有多 GB 数据库仍须在目标电脑上验收。

## 8. 下一步研发建议

优先增加发行版独立签名与可验证发布者身份；形成覆盖真实 Windows/macOS/Linux 机器的升级演练矩阵；对数据库结构迁移引入明确 schema version 与回退策略；若转成独立 EXE 安装包，再采用平台原生代码签名及安装器机制。科研分析侧继续推进表格结构解析、跨论文实验条件归一化、SynthesisAgent 和证据约束 RAG。这些科研 Agent 可独立研发，不应嵌入自更新入口。
