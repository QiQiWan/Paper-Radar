# Paper-Radar v1.12.0：全文证据精读与推荐质量评估完整设计

版本：1.12.0｜日期：2026-11-04｜研发基线：v1.11.0

## 一、设计结论与定位

下一阶段最有价值的改进，是将已有论文追踪工作流推进到“可核对原文证据的阅读助手”，并以人工标注的可复现指标检验推荐质量。v1.11.0 的主题级阅读反馈、AI 标题摘要排序和 OpenAlex 语义发现已提供检索基础；继续叠加无证据的长文本生成会增加误判风险。本轮采用轻量级、可降级、可验证的增量架构，不重建数据库，也不更换现有本地 Web 工作台。

本轮完成：①本地 PDF 按页全文索引；②有页码和原文引文的 AI 阅读卡片；③独立的全文查询与主题范围控制；④将已核验卡片注入 Word/Markdown 报告；⑤人工标注模板、离线推荐指标；⑥异常情况下的证据失效、客户端降级及操作说明。

本轮未完成：PDF 公式语义重建、表格数值抽取、OCR、图像理解、全量多文献 RAG、学术结论的自动真伪验证、面向公网的多用户服务。它们应在全文解析质量和人工验收通过后逐步建设。

## 三、目标工作流和用户操作

### 3.1 一般文献追踪

1. 选择研究主题，输入研究关键词或使用 Zotero 收藏夹。
2. 使用 arXiv、OpenAlex、Crossref 等已有来源获取元数据、去重、推荐并生成报告。
3. 在论文库挑选值得阅读的论文，合法下载开放获取 PDF。
4. 点击“全文证据”，选择“解析本地 PDF”；解析完成后可使用原文检索，**不需要 API Key**。
5. 如需深入分析，再点击“生成 AI 阅读卡片”，阅读发送范围提示并确认。模型只看到经过选择和截断的正文片段。
6. 核对阅读卡片中的具体页码和原文引文。可复制 Markdown 笔记，或者重新生成 Word/Markdown 汇总报告。

全文阅读功能是按需启动的，不会让日常自动检索默认为每一篇论文解析 PDF 或调用模型。旧论文仍然可以只凭题名、摘要和推荐理由进入报告。

### 3.2 版本发布与更新提醒

继续使用 v1.10 引入的 GitHub `/releases/latest` 检查方案：在本地 Web 工作台后台异步请求、按配置间隔缓存、发现比本地高的正式发布版本后显示官方链接。新版本**不会自动下载安装**。发布者需创建公开、非草稿的正式 Release，单独打 Tag 或上传代码不会触发提醒。升级前保留旧目录中的 `settings.json`、`data/`、`downloads/`、`reports/`、`logs/`。

## 四、技术架构及接口

```text
工作台：论文库 -> 全文证据对话框
                 |
                 +-- GET /api/fulltext/status  -> 校验 PDF 哈希 / 读取卡片
                 +-- GET /api/fulltext/search  -> FTS5 / LIKE 原文检索
                 +-- POST /api/job index_fulltext  -> 本地 pypdf 分页提取
                 +-- POST /api/job analyze_fulltext -> 用户确认 -> LLM
                                                            |
SQLite papers(topic metadata) ------------ fulltext_documents (PDF 哈希/解析范围)
       |                                     fulltext_chunks (页码/片段)
       +-- topic_papers (主题级关系)         fulltext_claims (结论/引文/页码/模型缓存键)
                                               |
                                            Word / Markdown 报告

独立的推荐评价：topic_papers -> 人工标注 CSV -> evaluation.py -> JSON 指标
```

沿用 `paper_radar/webapp.py` 的本机 Host 检查和写操作 Token，新增 HTTP 仅限本机。前端展示论文与模型文本时必须转义 HTML；`/api/pdf/{paper_id}` 仍通过现有下载目录白名单检查，拒绝任意文件路径。

新增主要模块：`paper_radar/fulltext.py` 管理全文索引、状态、证据检索和 AI 卡片；`paper_radar/evaluation.py` 管理离线标注与评价。配置与文章数据继续由现有 `core.py` 和 SQLite 管理。仅增加 `pypdf` 依赖，无需部署向量数据库、消息队列或独立 Web 服务。

## 五、PDF 解析、切分与证据定位

### 5.1 输入与边界

只接受 Paper-Radar 自身 `downloads/` 目录中已记录的本地 PDF，拒绝任意传入绝对路径、越级路径和非 PDF 文件。不尝试绕开订阅服务或 DRM。单篇 PDF 最大50MB，默认最多解析100页、600个文本片段，每页文本最多40,000字符；这些都是防止资源无限扩张的约束，并不保证对恶意压缩流的绝对防护。

使用 `pypdf` 读取文本层，并保留实际 PDF 页码。章节标签通过页首模式匹配近似识别，用作导航提示，不能当作精确的学术章节判定。片段采用约1,350字符的窗口及重叠，优先在句子和换行处断开。

扫描版、数学符号、复杂表格、脚注、多栏错序可能无法准确抽取。没有提取到文字时显示 `no_text`，不调用外部 OCR，也不生成虚构的全文分析。解析达到页数和片段限制时标记 `partial`，报告明确说明覆盖范围。

### 5.2 增量与防过期

每篇 PDF 存储 SHA-256 指纹和解析器版本。文件不变时重用已有索引；文件内容改变时，重新解析并在单个事务内清除旧片段和 AI 卡片。即使用户绕过系统直接替换 PDF，全文搜索、阅读卡片查看以及新导出的 Word/Markdown 报告也需核对实际文件哈希，旧引文不会继续作为新报告依据。

`fulltext_documents` 记录页面总数、索引页面数、文本片段数、最近更新时间与状态；`fulltext_chunks` 记录 PDF 页码、近似章节和原文；`fulltext_claims` 记录分类、解释、引文、页码、片段 ID、文件指纹及模型缓存键。可用 SQLite FTS5 则优先采用全文索引，否则使用有界 `LIKE` 检索。

## 六、大模型精读及可信度控制

### 6.1 模型输入

点击生成卡片前，页面明确提示会向当前模型服务商发送**最多12个选择的正文片段**并可能产生费用。模型接收论文题名、页面、近似章节与每段最多850个字符的内容。输入按照章节覆盖、页码分散和前文背景综合选择。**这只是采样的部分正文**；若实验数字出现在没有被选中的表格里，模型应输出缺少信息。

外部 PDF 文本始终作为低信任数据处理。系统提示词禁止模型执行论文中的指令，但提示词并不能替代隔离、输入限幅和严格结果校验。

### 6.2 输出契约与拒绝条件

模型只能输出 JSON `{claims:[{category,statement,chunk_id,quote}]}`；`category` 属于 `method/experiment/limitation`，最多保留9条。每条必须提供合法片段 ID、对应段中的**连续原文引文**和中文解释，拒绝伪造引文、无效 ID、非法分类、非法 JSON 和部分未提供依据的数字。验证未通过时不持久化结论，报告不会出现无来源的“已验证事实”。

当前的数值门槛采用字符串对照，仍可能漏检单位换算、数字近义写法、因果性推断和跨句上下文错误；**“有引文”不能等同于“结论真实”**。前端必须保留“辅助阅读、需核对原文”的提示。缓存绑定 PDF SHA-256、模型、接口和提示词版本，避免换模型或改文献后复用错误分析。

### 6.3 后续需要补强的验证

将表格识别和表格编号定位作为独立工作，不要让正文搜索猜测表格数字。人工构造一个包含多栏、公式、附录、扫描页和错误引文的测试集，记录正文提取覆盖率、引文准确率、事实错误率和平均处理成本。长 PDF 解析建议进一步采用隔离子进程、CPU/内存限制和可恢复任务队列，避免异常 PDF 阻塞整个后台线程。

## 七、推荐效果评估：必须以人工标注为基准

### 7.1 数据标注与复现

在已检索论文库中按主题导出前50篇（可调）的人工标注模板，包含 `topic_id,paper_id,label,rank,title,source,published,url,notes`。研究人员根据阅读目标填写 `label`：0=无关，1=弱相关，2=相关，3=高度相关，其他列不必修改。建议每个主题先标注50–100篇，并补充被系统遗漏但人工认为相关的文献，以免仅评价模型自己检索到的样本。

```powershell
python -m paper_radar.evaluation --db data/papers.sqlite3 --export-template reports/推荐人工标注模板.csv --max-per-topic 50
python -m paper_radar.evaluation --db data/papers.sqlite3 --labels reports/推荐人工标注模板.csv --k 10 --out reports/推荐质量评估.json
```

第二条命令必须在人工填写标注后执行。指标：Precision@K 的保守下界、人工已标注集合内的 Recall@K、NDCG@K、MRR，以及 Top-K 标注覆盖率。**未标注文献不是已知无关论文**：当前评价为了给保守边界将其记作0，并明确报告覆盖率；Recall 的分母仅为提供的人工标注相关文献，不能声称它表示整个研究领域的完整召回率。

### 7.2 推荐对比的实验要求

对比 v1.11 关键词排序和 v1.12 可选 AI/语义发现，需要固定同一检索样本、主题描述、时间窗口、评估集及预算；基线和候选系统都应保存 Top-K 排序快照。单独报告：P@10、NDCG@10、标注覆盖率、实际检索覆盖、每100篇消耗的 Token/费用和延迟。没有实际标签与实验结果时，本项目不宣称已经达到任何具体准确率。

## 八、界面与任务可靠性

论文库卡片只在本地 PDF 存在时显示“全文证据”按钮。弹窗优先显示本地索引状态和阅读卡片；底部提供原文片段检索。全文索引任务与 AI 分析任务共用现有后台任务锁和进度记录，同一时刻只运行一个任务；可查看任务状态，不阻塞其他页面的阅读。PDF 提取失败或模型超时不应导致历史论文库、下载内容和已经生成的报告丢失。

界面用用户熟悉的“解析本地 PDF”“生成 AI 阅读卡片”“查找原文”等词语，复杂参数放在设计与开发文档。移动端弹窗宽度适配390px，长题名、证据片段自动换行。

## 九、风险清单、优先级和下一版本建议

| 事项 | 优先级 | 现状 | 下一步验收 |
| --- | --- | --- | --- |
| 本地 PDF 索引与页码 | P0 | 已实现 | 对真实多栏/复杂 PDF 验证覆盖率 |
| PDF 更新后证据失效 | P0 | 已实现 | 外部替换后搜索、展示和新报告均不使用旧卡片 |
| AI 引文校验及降级 | P0 | 已实现有限校验 | 伪引文、伪数字、无效 ID 不入库 |
| 推荐评估模板和离线指标 | P0 | 已实现 | 用户实际标注后产出可复现指标 |
| 实验表格、公式、图表证据 | P1 | 暂未实现 | 表格/图编号定位、独立数值复核 |
| 多 PDF 同主题综合比较 | P1 | 暂未实现 | 对统一数据集和指标进行可比性检查 |
| 长 PDF 超时/资源隔离 | P1 | 有单篇大小和页数上限 | 子进程资源限制和断点续跑 |
| 词义级/跨语言 RAG | P2 | 仅原文关键词搜索 | Embedding+全文检索混合召回基准 |
| Zotero 允许后安全写入笔记 | P2 | 当前只读分析 | 权限核验、预览差异、撤销方案 |
| 多主题个性化检索定时策略 | P2 | 现有每日批量追踪 | 每主题独立计划表、失败重试 |

建议 v1.12.1 首先使用真实论文测试解析、完善消耗与人工标注基准。v1.13 再建设表格实验比较和证据导向的专题周报。v2.0 可考虑可追溯文献 RAG、科研问题的持续监测和授权 Zotero 回写。任何新模块都须坚持原始文献可核查、来源许可和用户费用可控。

## 十、验收边界及发布条件

本轮单元与本地 HTTP 测试采用无网络的 PDF 样本、模拟模型响应和 SQLite 隔离库。真实服务商 API、真实出版社访问权限、Windows 计划任务、Zotero 桌面版本和扫描文献仍需运行电脑的人工验收。源码发布前核查 `LICENSE`、NOTICE、第三方依赖、无用户 PDF/数据库/密钥、自动更新正式 GitHub Release，以及新版截图与文档的一致性。
