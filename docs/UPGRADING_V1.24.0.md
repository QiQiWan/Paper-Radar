# v1.24.0 升级、配置和实机验收

## 上线前准备

本版本 Web/Worker 与桌面程序代码可以直接替换 v1.23.0 发行文件，但用户工作区 SQLite 会由 v6→v7 单向迁移；不能在新数据库上直接降级启动旧源码。

1. 停止公网 Web 服务和所有科研 Agent Worker。确认没有 PDF 解析子进程、后台迁移或自动更新器仍占用源码目录。
2. 使用 `tools/public_backup.py` 对包含 `accounts.sqlite3`、`users/<uid>/research.sqlite3`、`users/<uid>/pdfs/` 和运行状态目录的完整数据根目录做备份，使用其 `--verify` 逐文件校验；同时留存只读备份副本，记录源版本和文件 SHA-256。
3. 解压 v1.24.0 完整源码包，不覆盖生产环境数据目录、`.env`、systemd 配置和证书密钥。安装 `requirements.txt` 中的锁定依赖，若使用可选 PDF 布局/OCR 模块，按照 v1.23.0 的许可证约束自行安装。
4. 重启前先在隔离恢复环境执行 `python -m pytest -q` 和 `python -m tools.verify_public_deployment --help`，检查数据库首次打开时 v7 迁移成功，不破坏原有论文/报告。
5. 在生产目标环境先启动单个 Web 服务和独立 Worker，核对 `/api/public/health` 的版本 `1.24.0`；验证 TLS、真实代理 IP 配置、源码只读运行、磁盘额度与任务租约。

## 业务操作及验收场景

- 账号 A 上传某论文 PDF，索引并执行授权的模型提取；打开“查看证据”，确认原文引文、页码、实验数值及默认“待核对”状态可见。
- 在 PDF 证据右侧展开“核对实验字段与原文”，逐项填写数据版本、数据划分、单位、方向、汇总方法、训练预算、评估协议和核对依据。保存“人工核对通过”后刷新仍可看到状态，历史查询仅对本人和当前研究主题开放。
- 两篇不同论文各有经过人工核对的相同实验条件后，在跨论文比较界面登记“人工确认可比”。重新生成研究报告，必须显示用户复核状态与人工确认配对数量，**不得自动声称任何性能提升。**
- 将其中一篇的 `split` 或 `unit` 修改为不同条件，原配对必须失效，并显示不能直接比较的原因。
- 将证据标为“排除”，该项在 PDF 查看和复核历史中仍可见，但不再进入新报告；历史报告作为旧快照保留。
- 替换 PDF，旧审核及配对不能成为新文档的有效证据，历史日志仍保留；不同账号或不同研究主题不能读取和修改他人的记录，跨站请求缺失 CSRF 令牌必须被拒绝。
- 按照 v1.23.0 手册继续验证长篇论文解析、PDF 替换后的批次缓存清理和中途故障后断点续跑。用至少 30 篇独立标注的真实论文衡量页码召回、关系归属、定量比较错误率，并补充可比正例，方可讨论学术质量验收。

## 回滚与风险

停止所有服务 → 使用**升级前**的代码和完整数据备份（工作区 v6）同时恢复 → 检查 SQLite 完整性与文件权限 → 启动 v1.23.0。仅回滚代码会因迁移校验机制拒绝新库。升级后的人工复核历史不能通过数据库降级保留，因此应在回滚前单独备份变更快照。正式签名、Windows GUI、第三方 OCR/模型真实调用和多用户压力仍为独立验收工作。
